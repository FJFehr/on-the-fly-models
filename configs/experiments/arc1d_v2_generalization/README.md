# arc1d_v2_generalization

## Goal

Same question as `arc1d_hypermodel_looped_rope_canon_generalization`: can the hypernetwork
generalize to a task category it has never seen during training, inferring the task purely from
the 3-shot support examples at inference time -- and does a task-identity signal
(`hyper_head.num_tasks`, learned vs. frozen) help or actively hurt that generalization? Reported
on both exact match and token accuracy, not exact match alone -- the original experiment's 3-seed
results show accuracy is the steadier signal (see its README's Findings).

This is a rerun of that question at the **matched-scale architecture from
`arc1d_v2_hypernetwork_multitask`'s sizing sweep** (`shrink_matched_dim4.yaml`, 10,156 total
params) rather than the original experiment's much bigger `rope_canon_zhu_transformer`/
hidden_dim=64, 8-layer, ~1.58M-param recipe -- the same architecture
`arc1d_v2_compositional_generalization` uses, so the two v2-scale generalization experiments are
directly comparable to each other, not just to their respective originals.

**Naming note**: this experiment was originally built (and run once, seed 1) under the name
`arc1d_v2_looped_generalization` at a different, larger architecture (the dim=4 main-grid config,
`dim4_notd.yaml`/`dim4_frozentd.yaml`, ~200K total params). Renamed and resized here for two
reasons: (a) `n_loops=1` throughout -- no actual looping happens, "looped" only ever described the
`rope_canon_looped_transformer` *class* (which supports `n_loops>1` but isn't using it), not
something specific to this experiment, and every other flat (`n_loops=1`) experiment in the v2
story omits "looped" from its name; (b) to match `arc1d_v2_compositional_generalization`'s
architecture exactly rather than leaving the two v2-scale generalization experiments on different
hypernetwork sizes. The original ~200K-param run's results are superseded, not carried over here.

## Reusing the original experiment's design

Nothing about the *task* changes, only the architecture:

- Same 5 held-out categories, same siblings, same rationale for the choice (a structurally
  similar category left in training) -- see
  `arc1d_hypermodel_looped_rope_canon_generalization/README.md`'s "Held-out tasks" table.
- Same mechanism: each leaf's `task_categories` drops exactly one of the 15 categories (the
  held-out one) while `val_task_categories` keeps the full 15, so `results.txt`'s automatic
  per-category breakdown (`val_query_exact_match_by_task_<category>`,
  `val_query_accuracy_by_task_<category>`) reports both the held-out category's zero-shot score
  and the in-distribution scores from the same run.
- Config naming: `arm_<short_name>_<variant>.yaml`, generated by
  `scripts/gen_v2_generalization_configs.py`.

**Two deliberate deviations from the original experiment's grid**, per direction: only 14
categories (`1d_recolor_cmp` dropped, matching the main v2 story's convention rather than the
original experiment's 15), and only 2 of the original 3 task-identity variants built (`notd`,
`frozentd` -- plain `td` dropped entirely, per `arc1d_v2_hypernetwork_multitask`'s own precedent:
"historically bimodal/unstable"). Run at 3 seeds (not 1), matching the rigor of the original
experiment's full grid.

## Architecture

Identical to `arc1d_v2_compositional_generalization`:

| Component | Value |
|---|---|
| Target model | `rope_canon_looped_transformer`, `hidden_dim=4`, flat (`n_loops=1`) -- 1,204 params (at this experiment's `task_encoding.embedding_dim=4`) |
| Hypernetwork encoder | `rope_canon_transformer` (plain, non-Zhu), `hidden_dim=4, num_layers=1, output_dim=4` |
| `hyper_head.bottleneck_dim` | 8 |
| Generation | Dense (`lora_adapter: false`) |
| Trainable params | 10,088 (`notd`; frozen task-indicator projection in `frozentd` adds ~72 more non-trainable params) |
| Optimizer | Muon (`muon_lr=0.005, muon_momentum=0.95`) + AdamW aux (`lr=0.001, wd=0.01`) |
| Budget | `N_supervision=1, max_steps=8000, warmup_steps=800` |
| `save_checkpoints` | `false` -- unlike the compositional-generalization experiments, the
held-out score comes from this run's own validation loop, no separate eval script/checkpoint needed |

## Arms

5 held-out categories x 2 variants x 3 seeds = 30 jobs:

| Variant | `hyper_head.num_tasks` | `hyper_head.freeze_task_indicator` |
|---|---:|---:|
| `notd` | `null` | `false` |
| `frozentd` | `18` | `true` |

## Running

```bash
# Default: seeds 1, 2, 3, all 10 arms (30 jobs).
bash scripts/run_arc1d_v2_generalization.sh

# Split across nodes / override seeds, same convention as the original experiment:
SEEDS_OVERRIDE="2" bash scripts/run_arc1d_v2_generalization.sh
```

## Reading results

Same as the original experiment: pull `val_query_exact_match_by_task_<held_out_category>` and
`val_query_accuracy_by_task_<held_out_category>` out of each arm's `results.txt` across the 3
seeds, and compare `notd`/`frozentd` at this much smaller scale against that experiment's
3-seed findings (3/5 categories are a robust exact-match-0 null result regardless of variant;
the other 2 show noisy, seed-dependent partial success not cleanly attributable to `frozen_td`;
token accuracy essentially tied across variants at 0.850-0.864). Also worth comparing directly
against `arc1d_v2_compositional_generalization`'s zero-shot results, since both now share the
identical architecture.
