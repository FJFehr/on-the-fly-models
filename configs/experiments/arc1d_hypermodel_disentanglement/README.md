# arc1d_hypermodel_disentanglement

## Overview

These experiments test whether a hypermodel can represent multiple distinct tasks simultaneously without conflating them.

**Setup:**
- **Hypernetwork (encoder):** Transformer (hidden=64, 4 heads, 2 layers) reads a task's support pairs and produces a task vector
- **Bottleneck:** Hierarchical pooling compresses the task vector to `projection_dims` (default: `[16]`)
- **Target model (decoder):** Bidirectional RNN (hidden=22, 2 layers) whose weights are generated by the hypernetwork from the bottleneck vector
- **Data:** `data/arc_1d_all_tasks_augmented` — 681k train examples across 17 task categories, 1000 variants per task

The bottleneck is the key constraint: if the model must solve multiple task types, the bottleneck must encode which task is being solved without conflating the representations.

---

## Data Augmentation

The dataset `data/arc_1d_all_tasks_augmented` is generated from the raw `data/arc_1d` dataset using `scripts/augment_arc_1d.py`. Each task in the train split receives 1000 augmented variants via three transformations applied in order: colour permutation → shift → (no mirror).

**Build command:**
```bash
uv run python scripts/augment_arc_1d.py \
    --per-pair \
    --n-color-permutations 199 \
    --shifts 1 2 -1 -2 \
    --no-mirror \
    --task-categories 1d_move_1p 1d_move_2p 1d_move_3p 1d_move_dp 1d_move_2p_dp \
        1d_fill 1d_hollow 1d_flip 1d_mirror 1d_denoising_1c 1d_denoising_mc \
        1d_pcopy_1c 1d_pcopy_mc 1d_recolor_oe 1d_recolor_cmp 1d_scale_dp 1d_padded_fill \
    --output-dir data/arc_1d_all_tasks_augmented
```

(`1d_recolor_cnt` is excluded — see below.)

### Colour augmentation

Colour augmentation is the primary source of diversity. There are two modes and the script selects automatically per task category:

**Per-pair mode** (used for most tasks): each support pair and the query receive an independent injective colour mapping. Non-zero colours within a pair are remapped to a random subset of `{1…9}`, but different pairs in the same task instance may use completely different colours. This gives up to 9^k combinations (k = colours per pair), enabling a far larger augmentation space than global mode. 200 colour variants are generated per task.

**Global mode** (used for tasks in `GLOBAL_ONLY_TASKS`): a single injective colour mapping is applied consistently across all support pairs and the query within a task instance. This is required for tasks whose rule depends on colour identity being consistent across pairs — for example, where a specific colour marks the direction of movement, or where all pairs share the same input/output colour set and the model must learn the recolouring criterion. 200 colour variants are also generated here (with replacement if the colour space is exhausted).

Tasks using **global** augmentation:

| Task | Reason |
|------|--------|
| `1d_move_dp` | A specific colour marks the movement target; it must remain consistent across pairs |
| `1d_move_2p_dp` | Same — direction marker colour consistent within each task instance |
| `1d_scale_dp` | Scaling marker colour consistent within each task instance |
| `1d_recolor_oe` | The input colour and both output colours are identical across all pairs and the query; per-pair would create artificially inconsistent colour sets |
| `1d_recolor_cmp` | Same — colour set is globally consistent within each task instance |

Special case: `1d_mirror` uses per-pair augmentation but colour 9 (the semantic pivot) is never permuted and is never a remap target. This is enforced by `FIXED_RULE_COLOURS` in the script.

`1d_recolor_cnt` is excluded from this dataset. Its recolouring rule maps a single input colour to many output colours depending on run-length counts — making it the most complex recolouring variant. It will be handled separately once its augmentation constraints are fully understood.

### Shifts

After colour augmentation, each variant is shifted in both directions by padding with background zeros: `[+1, +2, −1, −2]` plus the original unshifted position = 5 shift positions. Positive shifts prepend zeros (content moves right); negative shifts append zeros (content moves left). Sequence length increases by `abs(shift)`. No content is discarded.

Shifts are safe for all task categories: adding background padding does not change the rule relationship between input and output.

### Contamination filter

After augmentation, any train example whose exact content `(support_inputs, support_outputs, query_input, query_output)` matches a dev or test example is removed. Dev and test splits are passed through unchanged.

## Existing Experiments

### Individual tasks (baselines)

| Config | Task categories | Result |
|--------|----------------|--------|
| `move_1p.yaml` | `1d_move_1p` | 100% — works |
| `move_2p.yaml` | `1d_move_2p` | 100% — works |
| `move_3p.yaml` | `1d_move_3p` | 100% — works |

Individual tasks solve perfectly, confirming the architecture and bottleneck capacity are sufficient for a single task.

### Mixed tasks (failing)

| Config | Task categories | Result |
|--------|----------------|--------|
| `mix_1p3p.yaml` | `1d_move_1p` + `1d_move_3p` | Fails both |
| `mix_1p2p3p.yaml` | `1d_move_1p` + `1d_move_2p` + `1d_move_3p` | Fails all |

Mixed tasks fail — the model cannot solve either task when both are presented.

## Hypothesis

The move tasks (1p, 2p, 3p) are structurally very similar — they differ only in the number of pointers being shifted. The 16-dim bottleneck may not spontaneously learn to disentangle tasks that share so much structure, collapsing to an average representation that solves neither.

**Confirmed by Exp 1:** Pairing move_3p with the structurally dissimilar denoising_1c task succeeds without any descriptor, showing the bottleneck can disentangle when tasks are sufficiently different. The failure of move mixes is a task similarity problem, not an architecture or capacity problem.

---

## Experiments

### Exp 1: Structurally different task (denoising)

**Motivation:** If the tasks are too similar, the bottleneck has no pressure to disentangle them. Pairing `1d_move_3p` (pure spatial shift, no pixel count change) with `1d_denoising_1c` (selective deletion of isolated noise pixels) introduces a qualitatively different task. If the bottleneck can separate these two, it confirms disentanglement is possible but the move variants are too similar to force it.

**Config:** `mix_3p_denoise1c.yaml`

**Result: Both tasks solved.** The model successfully disentangles and solves move_3p and denoising_1c simultaneously without any task descriptor. This confirms the hypothesis: structurally dissimilar tasks are naturally disentangled by the bottleneck, and the failure of the move mixes is due to task similarity rather than insufficient capacity.

---

### Exp 2: Task descriptor embedding (bottleneck injection)

**Motivation:** Rather than relying on implicit disentanglement, inject an explicit task identity signal — a learned indicator embedding per task category added to the pooled task representation before the projection MLP.

**Implementation:** `hyper_head.num_tasks: 18` enables a `Linear(18, 64)` that projects a one-hot task indicator and adds it to the pooled representation. Uses the global `TASK_CATEGORY_INDEX` (18 categories) so canonical IDs index correctly. Config: `mix_1p3p_task_descriptor_bottleneck.yaml`

**Result: Task descriptor successfully disambiguates tasks.** Explicitly providing task identity resolves the conflation problem. The model trains faster and converges more stably than without the descriptor.
