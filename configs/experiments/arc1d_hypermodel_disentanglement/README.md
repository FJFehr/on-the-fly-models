# arc1d_hypermodel_disentanglement

## Overview

These experiments test whether a hypermodel can represent multiple distinct tasks simultaneously without conflating them.

**Setup:**
- **Hypernetwork (encoder):** Transformer (hidden=64, 4 heads, 2 layers) reads a task's support pairs and produces a task vector
- **Bottleneck:** Hierarchical pooling compresses the task vector to `projection_dims` (default: `[16]`)
- **Target model (decoder):** Bidirectional RNN (hidden=22, 2 layers) whose weights are generated by the hypernetwork from the bottleneck vector
- **Data:** `data/arc_1d_move_augmented` — per-pair colour augmentation (200 colour variants × 5 shift positions = 1000 variants per task)

The bottleneck is the key constraint: if the model must solve multiple task types, the bottleneck must encode which task is being solved without conflating the representations.

---

## Existing Experiments

### Individual tasks (baselines)

| Config | Task categories | Result |
|--------|----------------|--------|
| `move_1p.yaml` | `1d_move_1p` | 100% — works |
| `move_2p.yaml` | `1d_move_2p` | 100% — works |
| `move_3p.yaml` | `1d_move_3p` | 100% — works |

Individual tasks solve perfectly, confirming the architecture and bottleneck capacity are sufficient for a single task.

### Mixed tasks (failing)

| Config | Task categories | Result |
|--------|----------------|--------|
| `mix_1p3p.yaml` | `1d_move_1p` + `1d_move_3p` | Fails both |
| `mix_1p2p3p.yaml` | `1d_move_1p` + `1d_move_2p` + `1d_move_3p` | Fails all |

Mixed tasks fail — the model cannot solve either task when both are presented.

---

## Hypothesis

The move tasks (1p, 2p, 3p) are structurally very similar — they differ only in the number of pointers being shifted. The 16-dim bottleneck may not spontaneously learn to disentangle tasks that share so much structure, collapsing to an average representation that solves neither.

---

## Experiments

### Exp 1: Structurally different task (denoising)

**Motivation:** If the tasks are too similar, the bottleneck has no pressure to disentangle them. Pairing `1d_move_3p` (pure spatial shift, no pixel count change) with `1d_denoising_1c` (selective deletion of isolated noise pixels) introduces a qualitatively different task. If the bottleneck can separate these two, it confirms disentanglement is possible but the move variants are too similar to force it.

**Data:** `data/arc_1d_move3p_denoise1c_augmented` — same per-pair augmentation scheme as move (200 colour variants × 5 shift positions = 1000 variants per task, mirrors disabled). 80k train tasks total (40k per category).

**Config:** `mix_3p_denoise1c.yaml`

**Question:** Can the model solve both a move task and a denoising task simultaneously?

---

### Exp 2: Bottleneck capacity sweep (projection dims)

**Motivation:** The 16-dim bottleneck may have enough capacity to memorise a blended representation without disentangling. Two sub-experiments probe this:

**2a — Minimal bottleneck (`projection_dims: [2]`):**
Forces the tightest possible code for 2 tasks. Config: `mix_1p3p_bottleneck2.yaml`

**2b — Bottleneck 2 with projection (`projection_dims: [2, 32, 512]`):**
Same 2-dim bottleneck but with non-linear projections expanding back to weight-space, giving the model capacity to map from a tight code to target weights. Config: `mix_1p3p_bottleneck2_proj.yaml`

**Question:** Does a tighter bottleneck force better disentanglement, or does it make both tasks worse? Does adding projection capacity after the bottleneck help?

---

### Exp 3: Task descriptor embedding

**Motivation:** Rather than relying on implicit disentanglement, inject an explicit task identity signal — a learned indicator embedding per task category. Two injection points are tested:

**3a — Bottleneck injection (`num_tasks: 18`):**
A learned `Linear(18, 64)` maps a one-hot task indicator and adds it to the pooled task representation *before* the projection MLP. Tested on `1d_move_1p` + `1d_move_3p`. Config: `mix_1p3p_task_descriptor_bottleneck.yaml`

**3b — Input injection (`num_tasks_input: 18`):**
A learned `Embedding(18, 16)` adds the task indicator to *every input token* before the hypernetwork, like a positional embedding. This lets the hypernetwork attend differently depending on task identity. Config: `mix_1p3p_task_descriptor_input.yaml`

**Implementation:** `num_tasks` and `num_tasks_input` are new `hyper_head` config keys. Both use the global `TASK_CATEGORY_INDEX` (18 categories) so canonical IDs index correctly. The two options can be combined.

**Question:** Does explicit task identity resolve the conflation problem? Does injecting at the input vs the bottleneck matter?
