# arc1d_hypermodel_looped

## Goal

Have a hypernetwork generate the weights of `RoPECanonLoopedTransformer` — the smallest,
simplest looped backbone found by the capacity-ablation story (`hidden_dim=16`, no
block/loop skip, 11,760 backbone params; see `configs/experiments/arc1d_uniform_ablation`'s
L1 result) — instead of training that backbone directly. Phase 1 uses `n_loops=4` (not the
capacity story's `n_loops=8`) to keep the internal loop cheaper while the hypernetwork path
is being validated; `n_loops` does not affect parameter count (`middle_layer` is
weight-shared), so this is a compute/depth choice only, not a model-size change.

**Model size** (fixed regardless of `n_loops`): hypernetwork encoder + hyper head
1,736,784 trainable params, target model 11,920 params (11,760 backbone + 160 output head,
generated on the fly by the hypernetwork, not directly trained) — **1,748,704 total**.

## Backbone as hypernetwork target

`RoPECanonLoopedTransformer` gained an optional `use_output_head` flag so it can be
registered as a self-contained `TARGET_MODEL_REGISTRY` entry in `models/hypermodel_lightning.py`,
mirroring how `transformer`/`cnn`/`rnn` targets already work — `HyperModel` freezes the
target, generates its full flattened parameter vector (`hyper_head.low_rank_output` unset,
i.e. full MLP prediction, not low-rank — appropriate at this small param count), and applies
it via `functional_call` per task in the batch. Because the backbone's `middle_layer` is one
shared submodule called `n_loops` times, the generated parameter count is independent of
`n_loops`, same as when trained directly.

**Internal vs external looping:** `n_loops` is the backbone's own internal loop (one
autograd graph per `forward()` call, unchanged by the hypernetwork). `N_supervision=2` is the
*external* loop — `HyperModelLightning` now runs manual optimization, re-invoking the
hypernetwork (and therefore regenerating the target's weights) once per `N_supervision`
iteration per batch, so each iteration reflects the hypernetwork's just-updated parameters
from the previous iteration's optimizer step. This mirrors `LoopedSupervisedLightning`'s
existing `N_supervision` mechanism, composed with the hypernetwork call rather than a
directly-trained backbone.

## Data

`data/arc_1d_looped_augmented` — **the same augmented dataset used by the capacity-ablation
story** (`arc1d_recursion_ablation`/`arc1d_uniform_ablation`), built via:
```bash
python scripts/augment_arc_1d.py \
  --per-pair --n-color-permutations 199 --shifts 1 2 -1 -2 --no-mirror \
  --output-dir data/arc_1d_looped_augmented
```
~1000 variants per base task (200 colour permutations × 5 shift positions). Deliberately
**not** `data/arc_1d_augmented` (the older ~242-variants/task recipe used by
`arc1d_hypermodel_augmented`) — using the capacity story's exact recipe keeps this
comparable to the directly-trained result. Val/test read from the unaugmented dev/test
splits. Schemas are identical between the two augmented datasets
(`task_category, task_id, sequence_length, support_inputs, support_outputs, query_input,
query_output`), so this is a drop-in `data_dir` swap, not a format change.

`1d_padded_fill` is excluded — it was never part of the per-task `arc1d_hypermodel_augmented`
configs this phase mirrors (only the multi-task `mixes/`/`_td` configs include it), so it
simply never enters the picture here.

## Roadmap

1. **Individual tasks (current phase).** One hypernetwork target per task category, no
   task descriptor, no mixing — 17 configs (all `arc1d_recursion_ablation` task categories
   except `1d_padded_fill`), generated by `scripts/gen_hypermodel_looped_configs.py`, run
   over 3 seeds via `scripts/run_hypermodel_looped.sh` (51 jobs).
2. **Small mix.** `1d_move_1p` + `1d_move_2p` + `1d_move_3p` together, to validate that
   multi-task hypernetwork training works at all before scaling further.
3. **Task-descriptor mix, "simple" 11-task subset.** Once mixing works, add the
   `hyper_head.num_tasks` one-hot task descriptor (same mechanism as
   `arc1d_hypermodel_augmented_td`) and train on the same reduced 11-task subset already
   established there (`rnn_simple_td.yaml`): `1d_denoising_1c, 1d_denoising_mc, 1d_fill,
   1d_hollow, 1d_mirror, 1d_move_1p, 1d_move_2p_dp, 1d_move_dp, 1d_pcopy_1c, 1d_pcopy_mc,
   1d_scale_dp`.
4. **Low-rank variant, same 11 tasks.** Repeat step 3 with `hyper_head.low_rank_output: true`
   (matching `arc1d_hypermodel_augmented_td_low_rank`'s existing 11-task configs), to compare
   full vs low-rank weight generation on the looped backbone.

Steps 2-4 are not yet built.

## Running

```bash
python scripts/gen_hypermodel_looped_configs.py
bash scripts/run_hypermodel_looped.sh        # 8 GPUs, seeds 1-3, skips already-completed runs
bash scripts/run_hypermodel_looped.sh 4
```
